# 大文件生产变更安全协议（2026-10-17）

## 目的

GitHub Contents 的文件更新接口是整文件替换接口，不能把“接口成功”解释为“只修改了目标片段”。涉及大型脚本、workflow、规范或状态模板时，必须防止截断、换行归一化、重复 import、未预期重写和语义漂移。

## 强制变更流程

后续所有代码、workflow、规范和大于小型配置的文件变更，统一采用：

1. 从最新 `main` 建立独立分支；读取 INDEX 和所属正式规则。
2. 优先使用本地 Git 工作树与 `apply_patch` 做最小增量修改；不得把 GitHub Contents 整文件回写作为默认编辑方式。
3. 若工具边界迫使使用 Contents，必须先保存原始 blob SHA，并在提交后对比 PR diff；发现超出预期的行、文件、换行或 import 变化时立即停止，不得合并。
4. 合并前必须完成：
   - PR changed-files 与 unified diff 检查；
   - Python `py_compile` 或等价语法检查；
   - 受影响模块的 targeted tests；
   - 对 workflow/config 执行结构化解析或 schema 检查；
   - 对大文件执行首尾片段和关键符号回读。
5. 合并后必须从 `main` 回读变更文件，核对 commit、blob SHA、关键符号和测试结果；不能只依据 merge API 的成功响应。

## 变更范围护栏

- 预期只改一个片段时，PR diff 不得出现整文件删除重建。
- import、换行、编码和无关格式变化均视为需要解释的变更。
- 任何大文件 diff 无法明确归因时，回滚该分支并从最新 main 重新实施；不得在不确定状态上继续叠加。
- Contents API 适合小型独立文件、请求 ingress 和明确的整文件生成物；不适合作为大型源码的常规编辑器。
- PR diff、语法检查和合并后回读是共同门禁，任何一个缺失都不能声称安全完成。

## 责任边界

该协议是生产变更与并发治理域的执行护栏，不新增业务规则、状态、writer、workflow 或通知链。它不能替代代码审查、CI、真实 E2E 和所属正式规范。
