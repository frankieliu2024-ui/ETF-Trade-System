# 生产变更与并发写入协议 V1.5

> 本文是ETF系统**生产变更、状态写入与并发治理域的唯一规范性规则来源（Single Source of Truth）**。它属于技术维护规范，不产生交易规则、风险许可、Trial／Confirm、金额或买卖动作；GitHub `main` 仍是云端唯一主版本，交易规则仍只以 `ETF规则_MASTER.md` 为准。workflow、脚本、状态文件、writer ownership声明和测试只负责实现、运行、记录或验证本文规则，不得独立创造第二套生产写入、文件所有权、并发、latest-main、回滚或持久化规则。运行事实以当前 `main` 的实际workflow、脚本和状态为准；治理规则解释以本文为准。若实现与本文冲突，视为实现漂移，必须修复实现，不得以现有代码反向覆盖本文规则。

## 目标

解决“多个修复各自正确，但因为同时基于不同版本、同时写共享状态或派生状态尚未追上真实事实，组合后出现回退、覆盖或误报”的问题。

系统允许多个问题同时诊断、研究和计算，但共享生产状态的正式写入必须满足：**并行诊断、隔离实施、串行集成、latest-main重放、组合验收。**

本文只定义稳定的生产治理语义与边界。具体当前writer清单、workflow名称、状态文件实际内容、HEAD、run id和运行结果属于机器运行事实；文中列出的当前实现用于明确受治理对象和审计边界，不应被解释为允许绕过最新 `main` 的真实实现状态。新增或调整正式writer、ownership、并发队列或持久化入口时，必须先或同时更新本文并通过现有系统一致性检查；不为此新增高频前置检查或阻塞行情主链。

## 固定执行协议

1. 多个问题可以并行诊断；任何涉及源代码、规则、provider、workflow或状态构建的修复，默认在隔离分支或隔离workflow中实施。
2. 不允许两个独立修复分别基于旧的同一 `main` 快照直接落生产。第一个修复合并并完成一致性检查后，第二个修复必须重新基于最新 `main` rebase、重放或重建。
3. 功能修复原则上只移植稳定源文件。`CURRENT.json`、`decision_context.json`、`research_context.json`、`system_consistency.json` 等动态状态应由最新 `main` 的正式生产链重新生成，不用旧分支动态快照覆盖新状态。
4. 会直接写 `main` 的 workflow 必须设置 concurrency，并在 push 前执行 latest-main 同步；禁止 force push。允许并行抓取和计算，但生产提交必须在最新 `main` 上重放自身拥有的文件。
5. 文件所有权优先于“最后写入者”。单一所有者文件不得由其他workflow持久化；共享写入必须属于明确的同一writer family并共享串行队列，或有明确合并规则。
6. PoC、shadow、capability validation 等尚未正式转化的验证任务默认不得直接写 `main`。其运行结果保留为短期 GitHub Actions artifact；需要进入生产时必须另行完成正式转化、生产合同登记和主线验收。
7. 三份人类可读正式事实文件虽然可由不同业务事件触发，但其低层文本写入必须统一经过 canonical formal-file mutation gateway；不得由各业务脚本各自复制 managed-block/upsert 实现。
8. 每个生产变更在最终落地后必须执行组合验收，而不是只验证本次修改：至少覆盖系统一致性、账户/成交勾稽、E2E状态、关键事实优先级和工作树/提交SHA。
9. **MASTER规则变更先归并、后升版。** 准备修改 `ETF规则_MASTER.md` 时，必须先针对同一问题域做一次最小充分规则缺口检查：已经存在但仅部分固化、依赖聊天习惯或能够与本次同一逻辑解决的稳定要求，应在不扩大问题域的前提下一次归并；不得为单一措辞、单一CASE或可一并解决的相邻缺口连续升级MASTER版本。归并检查不是全面重构授权，仍遵循最小必要原则；不同问题域、证据未成熟或需要独立研究验证的事项不得为了“凑一次版本”强行合并。规则变更合并前仍需基于最新 `main` 重放，合并后执行组合验收。

## 当前关键文件所有权

- `data/state/system_consistency.json`：只由 `.github/workflows/system-consistency.yml` 持久化。其他workflow可以临时运行一致性检查，但不得把该临时报告作为自己的生产状态提交。
- `ETF规则_MASTER.md`：任何自动workflow不得修改或持久化；只能通过明确的规则维护变更进入 `main`。
- A股核心 `CURRENT`、runtime和行情快照：`market-snapshot.yml` 是主生产链；`opening-auction-current-fallback.yml` 仅作为同一producer的可靠性备援，两者必须共享 `etf-market-snapshot-${{ github.ref }}` concurrency group。

## 正式事实文件 mutation gateway

三份允许自动维护的人类可读事实文件是：`ETF当前状态_DASHBOARD.md`、`ETF市场行情档案_2026.md`、`ETF交易复盘与经验库_2026.md`。它们共享唯一低层入口 `scripts/formal_file_mutation_gateway.py`。

业务职责仍保持分离：`scripts/sync_formal_files.py` 负责已确认账户事实的幂等维护；`scripts/process_state_sync_request.py` 负责已由ChatGPT形成的正式决策、真实成交和正式复盘事实编排；`scripts/apply_trade_fact_correction.py` 只负责已存在成交的券商/用户确认费用等事实纠错。统一gateway只负责目标白名单、managed block、upsert和原子写入，不推导任何交易结论。

`ETF规则_MASTER.md` 永远不在gateway允许目标中。任何业务脚本绕过gateway直接对 Dashboard、行情档案或经验库执行 `write_text`，或者尝试把MASTER加入gateway白名单，都必须被一致性检查拒绝。

## 动态状态 producer 合同

动态状态不采用“一律单一writer”的粗粒度规则，而按事实性质分为 canonical market state、derived rebuildable state 和 bounded repair。

### `data/state/CURRENT.json`

- 类型：`CANONICAL_MARKET_STATE`。
- canonical builder：`scripts/cloud_runner_snapshot.py`。
- canonical writers：`market-snapshot.yml`、`opening-auction-current-fallback.yml`。
- 上述两条链必须使用同一核心producer和同一A股并发队列；价格、行情时点、snapshot指针、market phase等市场事实只能由该链生成。
- `self-healing-watchdog.yml` 只有一个有限例外：当MASTER版本元数据与CURRENT不一致时，`scripts/runtime_self_heal.py` 只允许更新 `CURRENT.rules_version`；不得改价格、时点、market phase、snapshot路径或其他行情事实。

### `data/state/runtime_health.json`

- 类型：`CANONICAL_A_SHARE_RUNTIME_HEALTH`。
- canonical builder：`scripts/cloud_runner_snapshot.py`。
- canonical writers：`market-snapshot.yml`、`opening-auction-current-fallback.yml`。
- 海外、通知、研究、一致性和其他workflow不得把自己的临时运行状态写入A股 `runtime_health.json`。

### `data/state/decision_context.json`

- 类型：`DERIVED_REBUILDABLE_STATE`。
- canonical builder：`scripts/build_state_context.py`。
- 允许持久化的入口：`market-snapshot.yml`、`opening-auction-current-fallback.yml`、`self-healing-watchdog.yml`。
- 多入口不是多套算法。所有持久化版本必须调用同一个canonical builder，从当时最新正式事实重建；workflow不得手工拼接或局部覆盖decision context。

### `data/state/query_context.json`

- 类型：`DERIVED_REBUILDABLE_STATE`。
- canonical builder：`scripts/build_query_context.py`。
- 允许持久化的入口：`market-snapshot.yml`、`opening-auction-current-fallback.yml`、`overseas-preopen-pulse.yml`、`self-healing-watchdog.yml`。
- `system-consistency.yml` 可以临时运行builder用于审计，但不拥有 `query_context.json`，不得把审计过程中生成的版本作为自己的owned state持久化。

## 非生产验证任务

以下任务保留验证能力，但不属于正式生产writer：

- `.github/workflows/akshare-capability-poc.yml`：输出 `data/state/akshare_poc.json`，仅上传 Actions artifact。
- `.github/workflows/minute-source-poc.yml`：输出 `data/state/minute_source_poc.json`，仅上传 Actions artifact。
- `.github/workflows/minute-path-shadow.yml`：输出 `data/state/minute_path_features.json`，仅上传 Actions artifact。

上述文件可以在 runner 工作区临时生成，但不得作为 `data/state` 正式缓存提交到 `main`。PoC通过、shadow稳定或统计表现良好都不等于已经生产转化；真正接入正式行情、研究或decision context时，需要独立审查其数据身份、PIT、稳定性、下游使用边界和producer合同。

## 事实优先级

生产状态不能依赖“哪个workflow最后写入”。至少遵循：

- MASTER规则 > 派生状态和历史聊天；
- 用户确认或券商确认的实际成交 > 辅助权益/历史账本重构；
- 最新有效账户事实 > 旧Dashboard或缓存；
- 更新的正式复盘事实 > 辅助历史重构；
- 真实provider数据时点 > workflow计划时间；
- 最新 `main` 的正式源文件 > 旧分支生成的动态状态。

## 自动检查

`scripts/check_production_mutation_protocol.py` 负责静态检查当前workflow和正式维护脚本：

- 自动发现直接 push 到 `main` 的workflow，检查 concurrency、latest-main同步和禁止force push；
- 检查单一所有者文件和A股共享writer family；
- 检查 `CURRENT.json`、`runtime_health.json`、`decision_context.json`、`query_context.json` 的producer合同和bounded repair；
- 检查PoC/shadow workflow保持只读并通过Actions artifact留档；
- 检查 canonical formal-file gateway 存在、仅允许三份事实文件且明确拒绝MASTER；
- 检查三个登记业务调用者均通过gateway写正式事实文件；
- 扫描常见 `DASHBOARD/ARCHIVE/EXPERIENCE.write_text` 直接绕过模式，发现即FAIL。

该检查接入正式 `scripts/check_system_consistency.py`。出现正式文件gateway绕过、未登记动态状态writer、canonical builder绕过、PoC/shadow重新取得main写权限、越权修复、未受保护的生产writer、单一所有者冲突或强制推送时，系统一致性必须FAIL，而不是继续把当前云端结构视为完整生产状态。
