## 二、三类任务唯一入口合同

### 1. ETF系统复核

- 任务身份：`ETF系统复核`
- 业务类型：Scheduled System Review
- 自动入口：`source=CHATGPT_SCHEDULED_SYSTEM_REVIEW_ACTOR`
- 手动入口：沿 current main 的 Scheduled Review 合同建立独立运行身份
- 自动节点：北京时间08:30、19:30；非适用交易日/节点才允许 SKIP
- 不创建或消费 Formal Decision 请求
- 不进入 `events/decisions/*.json`
- 不产生交易许可、订单或调仓动作

### 2. ETF交易复盘

- 任务身份：`ETF交易复盘`
- 业务类型：Scheduled Trade Review
- 自动节点：交易日12:30（以上午11:30为事实边界）、20:30完整日复盘；周日20:30周复盘
- 手动入口：不受自动节点时间限制
- 不创建或消费 Formal Decision 父请求
- 不写入或消费 BDS
- 不进入 `events/decisions/*.json`
- 不产生交易许可、订单或调仓动作

### 3. ETF正式决策

三种入口必须保持严格区分：

| 入口 | source | entry_mode |
|---|---|---|
| 对话窗口 | `CHATGPT_MANUAL_FORMAL_ANALYSIS` | `MANUAL_CONVERSATION` |
| 用户从任务界面手动启动 | `CHATGPT_MANUAL_SCHEDULED_FORMAL_ANALYSIS` | `MANUAL_SCHEDULED_TASK` |
| 系统自动节点启动 | `CHATGPT_SCHEDULED_FORMAL_ANALYSIS` | `AUTOMATIC_SCHEDULED_TASK` |

自动入口仅允许 current main 正式日历确认的交易日及北京时间09:00、10:00、11:00、13:30、14:30；两个手动入口不受自动节点时间限制。不得依据任务名称、当前时间、历史运行或旧对象猜测入口身份。

## 三、三类任务共同完成合同

每次运行必须：

1. 建立本次唯一运行身份；
2. 读取 current main 事实和所属业务规范；
3. 只生成一次唯一 `FINAL_CONTENT`；
4. 由 canonical completion owner 形成唯一完成请求；
5. 生成唯一 canonical event；
6. 由 canonical event 生成唯一 REPORT；
7. 统一进入 `notification_center`；
8. 由既有 PushPlus provider 原文发送；
9. 分别回读 completion、event、REPORT、notification_id 和 provider result。

通知成功不等于用户实际收到；provider success 不得被表述为用户已收到。失败时不得补绑历史对象、补发历史正文、创建第二请求、第二正文、第二 event 或第二通知。

## 四、链路边界

### Scheduled Review 共享链

ETF系统复核和ETF交易复盘共享 Scheduled Review completion、canonical review event、REPORT、notification_center 和 PushPlus 链。

PR #1393 已合并，合并提交：

其修复内容是统一 Scheduled Review completion 分支环境变量大小写，避免 Scheduled Review 被错误带入 Formal Decision 的 query_context 校验。

### Formal Decision 独立链

ETF正式决策使用独立的 BUSINESS_DECISION_SOURCE、formal completion、decision-notification workflow、Formal Decision event、REPORT 和 notification_center 路径。

不得把 Scheduled Review 的修复、状态、event 或 completion 直接套用到 Formal Decision；也不得让 Formal Decision 反向污染 System Review 或 Trade Review。

## 十、本周运行治理经验

版本：V1.0  
封存时间：2026-10-16（北京时间）  
适用范围：ETF系统复核、ETF交易复盘、ETF正式决策  
配套基线：`docs/ETF三类任务当前版本冻结封存_2026-10-16.md`  
唯一规则来源：`ETF_SYSTEM_INDEX.md`及其路由到的 current main 正式规范。

本文件固化本周真实运行中已经验证的失败经验和成功经验。它是治理经验，不替代 MASTER、数据规范、通知规范、Formal Decision协议、任务入口调度协议或生产变更协议。

## 一、必须先区分三类任务和两条通知链

### Scheduled Review 链

ETF系统复核和ETF交易复盘共享 Scheduled Review completion、canonical review event、REPORT、notification_center 和 PushPlus 链。

它们共享通知基础设施，但业务事实、任务身份、正文和 report_type 必须分别绑定本次运行，不能互相补绑。

### Formal Decision 链

ETF正式决策使用独立的 BUSINESS_DECISION_SOURCE、formal completion、decision-notification workflow、Formal Decision event、REPORT 和 notification_center 路径。

Formal Decision 不能因为通知失败就改走 Scheduled Review 链；Scheduled Review 也不能借用 Formal Decision 的 request、query_context、DWP、BDS 或 event。

## 二、本周已确认的失败经验

### 1. 正文成功不等于通知链启动

曾出现“正文已生成，但没有主动通知”。排查时不能从正文是否完整直接推断 completion、event、REPORT 或 notification 已发生。

必须逐层确认：

正文冻结 → completion 写入并回读 → canonical event → REPORT → notification_center → notification_id → provider result → 用户实际收到。

任何一层缺失，都只能报告停在该层，不能补绑历史对象或声称端到端完成。

### 2. Scheduled Review 被错误带入 Formal Decision 校验

真实根因是 workflow 环境变量大小写错误：

- 写入：`scheduled_review_completion`
- 后续读取：`SCHEDULED_REVIEW_COMPLETION`

导致 Scheduled Review completion 专用分支未生效，后续错误要求其匹配 Formal Decision 的旧 query_context。

治理经验：遇到“正文已生成、completion已写入但下游失败”，必须先检查：

- producer 分支标志是否真正传递；
- shell/GitHub Actions 环境变量大小写；
- 条件分支是否读到同一个变量；
- 是否被错误路由到其他业务链；
- 日志中的 expected/actual request 是否跨任务或跨链。

该问题由 PR1393 最小修复，不能通过新增旁路通知解决。

### 3. 失败运行不能使用历史请求或历史正文补救

本周多次出现旧 gate、旧 request、旧 query_context 或旧 completion 容易被误认为当前运行对象的情况。

治理规则：

- 当前运行必须新建唯一身份；
- 历史对象只能作为审计线索；
- request_id、task_run_id、occurrence_id、parent_request_id、report_id 和 content_hash 任一不一致，都不得绑定；
- 失败时不得补发历史正文；
- 不得创建第二请求、第二正文、第二 event 或第二通知。

### 4. provider 成功不等于用户收到

PushPlus 返回成功只能证明 provider 接受或发送成功，不能证明用户已经阅读或收到。

必须分别记录：

- notification_id；
- provider HTTP/result；
- provider 返回信息；
- 用户实际收到证据，如 PushPlus/微信截图或平台回执。

### 5. 任务身份不能靠任务名称或当前时间猜测

正式决策的三个入口必须区分：

| 入口 | source | entry_mode |
|---|---|---|
| 对话窗口 | `CHATGPT_MANUAL_FORMAL_ANALYSIS` | `MANUAL_CONVERSATION` |
| 任务界面手动启动 | `CHATGPT_MANUAL_SCHEDULED_FORMAL_ANALYSIS` | `MANUAL_SCHEDULED_TASK` |
| 系统自动节点 | `CHATGPT_SCHEDULED_FORMAL_ANALYSIS` | `AUTOMATIC_SCHEDULED_TASK` |

任务名称、计划时间、当前北京时间、历史消息和普通行情时间都不能替代入口元数据。

## 三、本周已确认的成功经验

### 1. 最小根因修复优于扩大重构

PR1393 只修正一个环境变量名称，没有改变：

- 业务判断；
- MASTER；
- provider priority；
- 交易权限；
- 监测范围；
- notification_center；
- PushPlus；
- 三类任务 Prompt。

合并后，ETF系统复核、ETF交易复盘均出现真实成功通知，证明修复应优先针对可复现的最小根因。

### 2. 必须用合并后的真实运行作为验收

CI通过、workflow显示成功或代码看起来正确，都不能替代生产行为验证。

本周合并后的真实基线：

- ETF系统复核：20:44，通知成功；
- ETF正式决策：20:51，通知成功；
- ETF交易复盘：20:58，通知成功。

验收必须同时包含：

- 用户正文；
- completion；
- canonical event；
- REPORT；
- notification_id；
- provider result；
- 用户收到证据。

### 3. 先回读对象，再判断是否闭环

对每次成功运行，至少回读并比较：

- task_id；
- task_run_id；
- occurrence_id；
- parent_request_id；
- request_id；
- report_id；
- report_type；
- full_content；
- content_hash；
- notification_id；
- provider result。

其中正文、REPORT、notification 和 PushPlus 必须使用同一份冻结正文和同一 content_hash。

### 4. 失败链和成功链必须使用同一业务链验收

不能因为失败过就增加第二 producer、第二 workflow 或人工旁路；也不能因为一次成功就跳过对象级回读。

正确做法是：

- 找到失败节点；
- 保持 producer 和 owner 不变；
- 修复节点间事实传递；
- 用同一条链重新运行；
- 对比失败和成功运行的实际对象。

## 四、本周证明无效或容易走弯路的排查方式

以下方式不能作为根因结论：

- 仅修改任务 Prompt；
- 看到正文完整就判断通知链正常；
- 看到 PushPlus provider 成功就判断用户已收到；
- 根据任务名称推测入口身份；
- 看到当前时间非固定节点就把手动运行 SKIP；
- 重新分析或重新生成一份正文；
- 扫描历史 completion 作为当前 completion；
- 直接写 event、REPORT、notification 或直接调用 PushPlus；
- 为单个失败案例新建旁路 workflow；
- 把 Formal Decision 的 gate、DWP、BDS 错套到 System Review 或 Trade Review；
- 把 System Review 或 Trade Review 的成功记录反向当作 Formal Decision 的完成证据；
- 因成功案例而关闭尚未完成对象级验收的总 Issue。

## 五、后续故障排查顺序

遇到“正文有、通知没有”时，严格按以下顺序，不跳层：

1. 确认本次入口身份和唯一运行身份；
2. 确认正文是否冻结且 content_hash 是否确定；
3. 确认 completion 请求是否写入并回读；
4. 确认 completion 是否绑定本次 request 和 occurrence；
5. 确认 canonical event 是否由唯一 owner 生成；
6. 确认 REPORT 是否由 canonical event 生成；
7. 确认 notification_center 是否产生本次 notification_id；
8. 确认 decision-notification 或 Scheduled Review 下游 workflow 是否真实运行；
9. 确认 provider result；
10. 最后才确认用户实际收到。

任何一步失败时，停止在该层，不创建第二条补救链。

## 七、当前治理结论

本周真正固化的核心经验不是“增加更多流程”，而是：

- 入口身份先确定；
- 运行身份只生成一套；
- 正文只生成一次；
- completion 只写一次；
- event 只由 canonical owner 生成一次；
- REPORT 只由 event 生成；
- notification_center 是唯一通知状态入口；
- PushPlus 只由既有通知链调用；
- 每一层都必须回读；
- 成功和失败都必须以当前运行对象为证据；
- 不用历史对象补当前运行；
- 不用抽象推测替代日志和对象回读。
