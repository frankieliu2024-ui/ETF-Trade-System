## 三、三类任务唯一业务边界

### 1. ETF系统复核

主链：System Review → Scheduled Review completion → canonical review event → REPORT → `notification_center` → PushPlus。

手动入口不受自动节点、交易日、周日、休市或同日已有复核限制；任何手动启动都按启动时点执行 PIT 并继续完整复核，不得改成 SKIP 或仅链路验证。自动入口仍按 current main 正式日历、market phase 和固定节点执行，不适用时才 SKIP。

System Review 必须输出完整系统复核正文，并包含本次全量一致性验收结果；一致性结果必须以本次启动时读取的 current main 和事实为准。System Review 不创建或消费 Formal Decision 父请求、BDS、Formal Decision event、交易许可或订单。

### 2. ETF交易复盘

主链：Trade Review → Scheduled Review completion → canonical review event → REPORT → `notification_center` → PushPlus。

手动入口不受固定节点、交易日、周日、休市或同日已有复盘限制；任何手动启动都按启动时点执行 PIT 并继续完整复盘，不得 SKIP、拒绝运行或改成仅链路验证。自动入口按 current main 合同判定 12:30、20:30、周日周复盘及事实边界。

Trade Review 不创建或消费 Formal Decision 父请求、BDS、交易许可、订单或调仓动作。

### 3. ETF正式决策

主链：入口身份 → 父请求 → request-bound facts/DWP → Formal Decision gate → 唯一 FINAL_CONTENT → BUSINESS_DECISION_SOURCE/BDS → Formal completion → decision-notification workflow → Formal Decision canonical event → REPORT → `notification_center` → PushPlus。

三种入口必须保持区分：

| 入口 | source | entry_mode |
|---|---|---|
| 对话窗口 | `CHATGPT_MANUAL_FORMAL_ANALYSIS` | `MANUAL_CONVERSATION` |
| 任务界面手动启动 | `CHATGPT_MANUAL_SCHEDULED_FORMAL_ANALYSIS` | `MANUAL_SCHEDULED_TASK` |
| 系统自动启动 | `CHATGPT_SCHEDULED_FORMAL_ANALYSIS` | `AUTOMATIC_SCHEDULED_TASK` |

手动入口不受自动节点限制；自动入口只在 current main 正式日历和节点适用时运行。Formal Decision 只允许用户人工确认和人工下单，不自动交易、不自动调仓、不改变交易权限。

## 四、共同正文与完成冻结合同

三类任务每次运行都必须：

1. 先读取 `ETF_SYSTEM_INDEX.md`，再按 INDEX 读取本任务所需正式规则、事实、协议、workflow 和状态；
2. 建立本次唯一运行身份；
3. 按启动时点读取 PIT 事实；
4. 只生成一次完整、唯一、用户可见的 FINAL_CONTENT；
5. 首次直接输出同一份完整正文；
6. 使用同一正文完成 completion、canonical event、REPORT、`notification_center` 和 PushPlus；
7. 逐层回读并比较身份、正文、report_id、content_hash 和 provider 结果；
8. 失败时停在实际失败层，不创建第二请求、第二正文、第二 completion、第二 event、第二 REPORT 或第二通知。

用户可见正文不得暴露内部 workflow/job、writer、BDS、canonical、gate、provider 等技术噪声；只表达业务事实、判断、风险、人工交易边界和必要的执行状态。北京时间只用简洁明确的时间表达。章节、标题、一级/二级编号和固定结尾必须按任务所属正文合同保持一致，不得因手动运行而缩短或删除既有章节。

## 六、今天固化的治理经验

### 1. 先确认是否是真实当前 main 问题

出现失败时，先区分：当前 main 代码/协议缺陷、执行器未提交 completion、workflow 被错误路由、对象回读失败、provider 失败、用户未收到。不能把所有“没有通知”都归因于 Prompt 或代码。

### 2. 只沿原业务链修复

最小根因修复优先。不得为单次失败新增旁路 workflow、第二 producer、第二 writer、直接写 event/REPORT/notification 或直接调用 PushPlus。已有 owner 能覆盖的场景，不新增 owner。

### 3. 运行失败与通知失败必须分层

正文生成不等于 completion；completion 不等于 event；event 不等于 REPORT；REPORT 不等于 notification；provider success 不等于用户实际收到。每层都要以本次运行对象回读为依据。

### 4. 失败重试不得制造第二对象

暂时性 workflow/锁/网络失败可沿原身份重试；身份冲突、事实冲突和 owner 拒绝必须 fail-closed。不能重写正文、恢复历史正文、补绑历史 completion、创建第二请求或重复通知。

### 5. 手动启动的核心语义是 PIT，不是节点验证

手动执行三类任务都必须按启动时点完整运行。固定节点和交易日限制只约束自动入口；不能把手动任务误判为自动节点 SKIP，也不能把正式任务改成“仅验证链路”。

### 6. 全量一致性验收必须属于 System Review 正文

System Review 不是只读 Dashboard 或状态摘要。每次启动都要执行一次全量一致性验收，并在完整正文中输出结果、WARNING/FAIL 的对象、影响和后续边界。较新的总览不得覆盖较旧但仍有效的风险、证据或一致性事实。

### 7. 经验库、Dashboard、strategy equity 必须共享 canonical projection

确认的费用、成交和账户事实必须由既有 canonical owner 一次处理，并回读经验库、Dashboard、strategy equity、行情档案等声明下游。不能只写经验库而遗漏其他投影；canonical 事实成功但任一下游未闭环时，必须标记 `PROJECTION_INCOMPLETE`。

### 8. 指令不是唯一约束，不能用指令掩盖实现缺陷

任务指令负责用户意图和显示合同；协议、代码、workflow、机器状态和测试共同决定真实运行。任何指令修正必须是最小必要修正，并先证明 current main 存在对应冲突或缺口。

### 9. 大型 JSON 的空读不能直接判定缺失

GitHub Contents 大文件出现空读或截断时，必须使用同一 GitHub Contents 来源回读、分段读取或提交对象核对后再下结论。不能以连接器一次空读替代事实缺失，也不能让连接器代替 builder 计算审计哈希。

### 10. 成功验收必须包含用户证据

代码、CI、workflow success、event 或 provider 200 只能证明对应层级。端到端成功还应保留用户可见通知证据；但没有用户证据时，仍应准确表述为 provider 成功，不得宣称用户已收到。

## 七、故障排查固定顺序

遇到“正文有、通知没有”或“任务失败”时，严格按以下顺序：

1. 入口身份与唯一运行身份；
2. PIT 事实和正文是否冻结；
3. completion 是否写入、回读并绑定本次运行；
4. producer 是否按任务链成功；
5. canonical event 是否由唯一 owner 生成；
6. REPORT 是否由 event 生成；
7. `notification_center` 是否生成本次 notification_id；
8. provider result；
9. 用户实际收到证据；
10. 若是数据维护问题，再回读所有声明下游投影。

任何一步失败，只报告停在该层；不跨层推断，不补绑历史对象。
