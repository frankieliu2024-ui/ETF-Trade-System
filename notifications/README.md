# 通知事件层

通知层只推送需要用户关注、确认或重新评估的事项，不生成盘中交易动作。现有 PushPlus 链保持不变，通知记录由 `data/state/notification_center.json` 管理。

## 通知价值与时段原则

PushPlus 是用户行动与高价值信息通道，不是 GitHub 运行日志出口。通知是否发送以“现在知道这件事是否有独立行动/关注价值”为准，不以 A 股是否正在交易为唯一条件。

- 不设置夜间免打扰或“非 A 股交易时间禁止推送”的硬限制；晚间、深夜、周末和休市日，只要出现确实需要用户确认/处理、会影响下一有效交易节点，或系统可靠性达到真实阻塞级别的事件，可以立即推送。
- A 股可交易时段内，已经形成的 Trial/Confirm 机会、风险许可实质变化、明确降低风险/退出动作等应及时推送，避免延迟损害执行质量。
- 收盘后允许推送完成当日闭环所必需的事项，例如最终账户事实缺失、成交待确认或未解释的持仓/资金变化。
- 普通行情波动、研究更新、GitHub 维护成功、自动修复成功、例行状态刷新以及无独立用户行动价值的变化，只保留后台事实，不单独 PushPlus。
- 海外或非 A 股时段信息不得把任意一笔原始涨跌直接包装成 A 股交易动作；固定节点总结和达到异动阈值的事件属于例外，因为它们具有独立的信息压缩与风险传导价值。
- 不新增“延迟到次日盘前”的消息队列。晚间通知可接受，因此保持“有价值立即推送、无价值不推送”的两态设计。

同一原则在所有通知入口统一适用：事件必须能回答“发生了什么、为什么现在值得知道、对ETF系统意味着什么、用户现在需要做什么”。若不能回答，则不应生成主动通知。

## 固定市场节点总结

固定节点总结不是简单涨跌播报，必须同时包含方向、横截面/区域结构、日内路径和对 ETF 系统的启示。节点总结不直接产生交易动作。

### 美股开盘/收盘

复用现有 `US extended-hours pulse`，不新增独立行情 workflow。美股时段按 `America/New_York` 自动处理夏令时和冬令时。

- 开盘总结：美东 09:35 后首个有效 REGULAR 脉冲；同一美股交易日只发送一次。
- 收盘总结：美东 16:05 后首个有效 POST_MARKET 脉冲；同一美股交易日只发送一次。
- 核心代理使用纳指100ETF代理（QQQ）和半导体ETF代理（SOXX）；不得冒充纳斯达克100指数（NDX）或费城半导体指数（SOX）正式指数值。
- `us_extended_hours_context.json` 保存现金盘开盘、收/现价、高低点、相对前收、相对开盘、低点修复、距高点回撤、日内区间位置，以及首小时/中段/尾段的5分钟bar路径变化。收盘总结必须表述日内路径，而不是只写最终涨跌。
- 盘前/盘后极端波动使用扩展时段相对最近现金盘收盘的变化，不得把上一现金盘旧涨跌重新包装成当前异动。

### A股开盘/收盘

复用现有 `ETF market snapshot → ETF decision notification` 链，不增加第二套 A 股行情采集。

- 开盘总结：09:35 后首个有效连续竞价节点，同一交易日只发送一次。集合竞价与连续竞价语义分开。
- 收盘总结：15:00 正式 close 节点形成后，同一交易日只发送一次。价格有效时点固定解释为 15:00；若provider在15:10/15:20补查，只作为观测时间单列，不冒充收盘价格时点。
- 摘要覆盖上证指数（000001）、科创50指数（000688）、创业板指（399006）、ETF横截面领先/靠后对象，以及 `intraday_path_features.json` 中的路径变化、低点修复、距高点回撤和近期斜率。
- A股收盘PushPlus只承担即时行情结构摘要；15:30的“ETF交易复盘”仍负责账户、风险许可、生命周期、资本效率、卖出判断和CASE的完整正式闭环，避免重复长文。

### 日韩台开盘/收盘

日韩台采用区域聚合通知，不为日本、韩国、台湾分别发送三套消息。

- 开盘总结：北京时间09:05后首个有效区域脉冲。此时日本、韩国已交易约一小时，台湾也已开盘，适合作为A股盘前/早盘跨市场背景。
- 收盘总结：北京时间14:30后首个有效区域脉冲，汇总日经225指数（N225）、韩国综合指数（KOSPI）、台湾加权指数（TWII），用于A股尾盘判断区域共振或背离。
- 每个对象尽量表述开盘、日内高低、当前/收盘、较前收或较开盘变化、低点修复、距高点回撤及区间位置；不同市场真实provider时点必须分别保留。
- 区域总结只提供“外部结构 → 本地传导”的证据，不直接产生A股ETF交易动作。

## 极端涨跌与突然涨跌

`send_market_shock_notification.py` 统一处理 A 股、美股、日韩台异动提醒。阈值只决定“是否值得占用用户注意力”，不是 MASTER 交易规则，不新增风险许可或生命周期等级。

当前通知层阈值：

- A股正式指数当日绝对涨跌约 ≥2.5%；监测ETF约 ≥4.0%：极端涨跌候选；
- 美股核心代理、日韩台正式指数当前有效阶段绝对涨跌约 ≥2.0%：极端涨跌候选；
- 相邻有效脉冲20分钟内绝对变化约 ≥1.0%：突然涨跌候选。

为了避免刷屏：同一对象、同一方向默认45分钟冷却；如果先出现“突然涨跌”后进一步升级为“极端涨跌”，允许打断冷却再通知一次。异动通知必须说明对象、当日/阶段变化、最近脉冲变化、为什么现在值得知道、对ETF系统的启示、用户动作和数据时点。

A股异动触发后要求重新检查相关指数、全部持仓ETF、全部观察ETF、唯一主候选、持仓风险收益和资本效率；但异动本身不直接下单。海外异动则进入最近有效A股决策节点，继续完成“外部结构 → 本地传导 → ETF自身反馈 → 机会判断”。

## 统一模板

节点总结统一采用：

1. `发生了什么`：节点、主要市场/指数/ETF方向和综合判断；
2. `日内路径`：开盘、高低点、低点修复、距高点回撤、分段走势、区间位置或A股离散脉冲路径；
3. `对ETF系统的启示`：说明风险偏好、区域共振/背离和下一交易节点需要验证什么；
4. `现在怎么做`：明确是否需要打开ETF项目刷新正式判断，或仅纳入下一节点；
5. `数据时点（北京时间）`：价格有效时点、provider实际观测时点、通知生成时间按需要分开；
6. `解释边界`：明确本通知不修改MASTER、不扩大权限、不自动下单。

异动通知统一采用：

`发生了什么 → 为什么值得现在知道 → 对ETF系统的启示 → 现在怎么做 → 数据时点 → 解释边界`。

正式交易机会、账户确认、成交确认和系统故障可保留其业务特有字段，但不得退回只有“状态变化，请重新检查”的低信息量模板。

## 生命周期

通知记录使用 `CREATED → SENT/WAITING_CONFIRMATION → CONFIRMED → ARCHIVED`，超过确认窗口进入 `EXPIRED`。同一 `source_event_id` 在未关闭或已关闭时不重复推送；失败/未发送不会被当作用户已确认。

需要确认的延迟执行事件统一标记为 `PENDING_EXECUTION_CONFIRMATION`。用户只能通过明确的“确认 / 否 / 补充成交明细”入口改变其状态；确认入口随后复用 `scripts/process_state_sync_request.py` 写入正式账户事实和 `events/trades`，不从最终持仓猜测成交。

确认成功后生成现有研究目录下的 `TRADE_COMPLETED_REVIEW_REQUIRED` 客观复盘待办，保留 `execution_date` 与 `confirmation_date` 两个时点。复盘待办不自动判断交易正确/错误，不修改 MASTER，不生成新的交易动作。

系统事件、A股节点总结/异动、收盘账户提醒和决策重评由现有 `.github/workflows/decision-notification.yml` 承载；美股节点总结/异动由现有 `.github/workflows/us-extended-hours-pulse.yml` 承载；日韩台节点总结/异动由现有 `.github/workflows/overseas-preopen-pulse.yml` 承载。没有新增行情provider、通知排队系统或平行交易规则系统。

## 微信通知的人机界面要求

每一条真实通知必须让用户在几秒内回答以下问题：

1. 发生了什么；
2. 是哪个模块、证券或账户事实；
3. 是否影响行情、账户或交易判断；
4. 用户现在是否需要操作、需要做什么；
5. 系统下一步如何处理。

测试通知标题必须明确包含“【测试】”，正文必须说明“不代表真实行情、账户、交易或系统故障”。真实系统异常标题必须明确包含“【真实运行异常】”及用户可理解的影响等级，例如“需要关注”或“影响交易判断”。

通知状态可以保存 `user_severity` 和 `user_action` 作为用户界面字段，但不得把内部 `E2E`、`BLOCKED`、`ESCALATE`、异常分类代码等直接当成主要微信文案。

历史 workflow 失败如果已被更新的 `main` 提交取代，不得作为当前真实故障继续推送。只有诊断对应当前 `main` 时，才允许发送系统故障通知；通知必须列明 workflow、Run ID、具体失败步骤、影响和用户动作。
