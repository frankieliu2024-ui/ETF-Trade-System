# ETF云端交易辅助系统上线前总评审

评审日期：2026-08-23  
当前规则版本：ETF波段交易系统 V2.2.15  研究池与数据接口正式吸收版

## 一、评审结论

结论：**方案有条件通过，当前不得宣布云端正式上线。**

本机行情链已经可运行：同花顺CLI认证有效，正式八ETF、上证指数和创业板指十项快照已验收，历史ETF接口也已完成补齐。但当前工作目录不是Git仓库，脚本写死Windows路径，凭据只在本机，当前Codex自动任务是绑定本地线程的Heartbeat，不能证明电脑关机后仍可执行。

最重要的产品边界已经核实：ChatGPT Scheduled Tasks可以定时运行和发送通知，但不能读取ChatGPT项目文件；GitHub连接在ChatGPT中主要用于读取和分析，不能作为无人值守写回主仓库的后端；Scheduled Tasks不提供Webhook触发。因此不能把ChatGPT Work任务设计成“直接运行本机同花顺CLI、读取本地四文件、提交GitHub”的云端主进程。

建议采用最小可行云端架构：GitHub Actions或等效云调度负责市场数据、质量检查、CURRENT和机器事件；ChatGPT/用户聊天负责读取最新节点、补充账户事实和形成最终交易判断；用户始终人工下单。手机原生ChatGPT通知只能列为条件能力，必须做端到端实测；在此之前应保留一个可靠的邮件或手机推送备援。

## 二、现状取证

### 1. 正式文件和版本

- MASTER、Dashboard、经验库、行情档案和接口规范均存在，当前标示为V2.2.15。
- MASTER明确规则唯一来源，禁止自动扩大权限；账户和真实成交仍以券商事实为准。
- 机器默认范围已经明确为八ETF＋上证指数＋创业板指；NDX及其他海外/商品对象为条件调用或独立来源。
- 现有专项回测、历史成交Excel和同花顺验收输出均保留，未发现规则文件被测试任务改写。

### 2. 数据和程序

- 同花顺CLI版本和认证已通过本机实测；远端快照十项成功。
- 长历史程序和盘中快照程序均存在，输出含原始响应、标准化文件和质量结果。
- 盘中快照脚本使用绝对Windows工作目录，不能直接迁移到Linux云Runner。
- 盘中快照脚本没有独立交易日闸门；周末查询可能返回最近收盘数据，必须由上层日历检查阻断。
- 当前历史Excel目录包含多个截止日期副本；需要冻结并标注基准批次，不能继续作为日常主数据入口。

### 3. Git和自动化

- 当前工作目录没有`.git`目录、没有远端地址，GitHub尚未成为主版本。
- 当前自动任务`ETF交易日五节点自动判断`为本机线程Heartbeat，提示词写死本机路径；旧截图提醒已暂停。
- 现有节点为09:30、10:30、13:30、14:30、15:10，不覆盖用户要求的09:25和11:30。
- 本机自动任务状态为ACTIVE不等于云端无人值守可用。

## 四、最大的技术风险

1. **执行宿主错位**：当前脚本依赖Windows绝对路径和本机凭据；电脑离线即停止，不能冒充云端。
2. **数据时点误判**：周末、午休、海外闭市或服务缓存可能返回旧值；必须使用交易日历、市场时段、provider timestamp和新鲜度闸门，失败时显示DEGRADED而非沿用旧值。
3. **写入竞态和版本冲突**：多个节点、重试或人工修改可能同时写Dashboard/CURRENT。必须使用GitHub Actions concurrency、唯一事件ID、父commit检查、原子文件替换和失败不提交。

## 五、最大的交易流程风险

1. **旧通知误决策**：用户点击10:30旧通知时必须读取CURRENT并切换到最新有效节点，旧节点只保留审计记录。
2. **账户事实过期**：行情正确不代表现金、持仓、成本和成交正确；金额和具体卖出份额必须在最近有效账户事实基础上形成。
3. **海外背景压制本地机会**：海外稍弱不能自动否决A股自身改善；顺序必须是外部结构→本地传导→目标ETF反馈→机会判断。

## 六、推荐职责分工

### Codex / 云端代码

负责代码、数据适配器、质量校验、CURRENT、事件日志、Git版本、备份、回滚和部署测试。Codex不替代用户作最终交易决定。

### GitHub Actions或等效云Runner

负责交易日闸门、同花顺及海外数据采集、标准化、质量报告、节点快照、CURRENT更新和机器通知。使用Secrets保存API Key；不写MASTER，不猜账户事实，不自动下单。

### ChatGPT Scheduled Task / Work

只作为可选的定时读取和通知层，前提是当前账号能读取经过授权的GitHub数据入口并通过端到端验收。它不是本机CLI运行器、不是Git写入器、不是Webhook消费者。若该能力不稳定，立即降级为手机推送＋用户进入当前聊天获取正式判断。

### ChatGPT聊天

负责读取最新CURRENT、确认有效节点、接收券商截图、按MASTER输出五项结构、给出固定金额或合法卖出份额，并记录用户最终人工执行结果。

## 七、CURRENT和节点状态设计

新增机器状态层，不把每个盘中节点直接堆入四个正式Markdown文件：

```json
{
  "market_date": "YYYY-MM-DD",
  "latest_valid_node": "1430",
  "captured_at": "Asia/Shanghai timestamp",
  "node_status": "READY|DEGRADED|BLOCKED|NON_TRADING_DAY",
  "supersedes": ["0930", "1030"],
  "snapshot_commit": "git sha",
  "data_freshness": {},
  "account_fact_at": null,
  "account_fact_status": "MISSING|STALE|VALID|CONFLICT",
  "needs_account_update": true,
  "last_trade_event_id": null,
  "rules_version": "V2.2.15",
  "generated_at": "Asia/Shanghai timestamp"
}
```

节点快照按`market_date + node + source_version`幂等保存。新节点生成后旧节点不删除，但标记为superseded。聊天入口始终以CURRENT的`latest_valid_node`为准，不以通知点击时间为准。

## 八、四文件云端维护边界

- **MASTER**：私有仓库中的稳定规则文件；只允许人工/Codex评审后提交，禁止无人值守自动修改。
- **Dashboard**：保留当前状态和下一节点；机器可更新市场时点、数据状态和待补资料，但账户、成交、金额、卖出份额必须来自用户确认事实。
- **经验库**：盘中真实成交先写不可丢失的事件日志，收盘后再合并CASE/OBS；不得用自动行情推断成交。
- **行情档案**：只保存数据源、口径、覆盖、异常和关键客观事实；完整日线放结构化数据层，不把交易判断写入档案。

四文件自动提交必须经过：拉取远端最新commit→父commit未变化检查→临时文件生成→schema/版本/职责检查→原子替换→提交→推送；冲突则停止并通知，不强制覆盖。

## 九、历史资产迁移方案

1. 四个正式文件、接口规范、专项回测Markdown、脚本和审计报告进入私有仓库。
2. 截至2026-08-21的历史成交Excel冻结为`baseline_2026-08-21`，保留原文件和校验哈希，不再日常覆盖。
3. `node_modules`、`__pycache__`、临时JSON、重复输出和大体积审计中间文件不直接进入主分支；完整专项输出打包为只读归档或Git LFS/Release资产。
4. 结构化新行情与四文件分离：`data/market/raw/`、`data/market/normalized/`、`data/market/audit/`、`data/state/CURRENT.json`。
5. 首次迁移前创建不可变备份，迁移后用文件哈希、行数、末日和规则版本双向校验。

## 十、节点和通知设计

目标节点：09:25、10:30、11:30、13:30、14:30、收盘完整数据生成后。09:25必须标记集合竞价/开盘前，不得冒充连续交易行情。

每个节点都生成短通知，即使没有机会也明确“任务正常、无新的主候选、无需处理”。通知只放节点、数据状态、风险背景、唯一主候选、重点持仓和是否需要用户处理；完整五项判断留在聊天或云端报告。

如果调度延迟，使用实际捕获时间和节点窗口，不伪造计划时间。收盘日线未生成时最多有限重试，随后DEGRADED，不用盘中快照冒充收盘。

## 十一、账户事实和真实成交

- 行情扫描可显示最近账户事实时间，但不得假定账户没有变化。
- 需要金额或具体卖出份额时，必须有用户确认的最新账户事实，且应覆盖最近已知交易事件之后的状态。
- 用户上传成交截图后，先生成唯一事件ID并保存原始凭证引用/哈希，再更新CURRENT；收盘后才整理CASE正文。
- 不把券商截图原图直接提交到普通仓库；应使用受限存储、最小化结构化事实和脱敏引用。
- 多设备或重复上传按事件ID幂等；时间冲突进入CONFLICT，不自行合并。

## 十二、故障降级

所有节点采用：`READY`、`DEGRADED`、`BLOCKED`、`NON_TRADING_DAY`。任何数据源、时区、交易日、账户事实或规则版本校验失败，都必须公开状态和原因。

- 同花顺失败：有限退避重试；仍失败则不产生新交易信号，保留上一节点只作历史参考。
- 海外源失败：不以旧值冒充实时，相关判断标为数据不足。
- GitHub冲突：停止写入、保存待提交包、通知人工，不强推。
- 节点漏跑：下一节点补采并写明漏跑，不补造历史节点。
- Work通知失败：使用备用手机推送/邮件；用户回到聊天后读取CURRENT。
- 日线未生成：只允许有限重试，收盘结论标记未完成。

## 十三、是否过度工程化

应删除或不实施：独立数据库、复杂服务编排、自动改MASTER、自动交易、重复的ChatGPT/Codex双重写入、每日全量复制历史OHLC、为每个海外对象建立独立任务。

保留最小组件：一个私有Git仓库、一个云Runner工作流、一套数据适配器、一份CURRENT、一个事件日志、一个通知通道、一个人工聊天入口。只有在最小架构通过故障测试后，才考虑拆分CASE/OBS多文件或引入数据库。

## 十四、建议部署顺序和验收门

### Phase 0：审计与备份

只读扫描、哈希、API Key位置检查、导出当前自动任务配置。验收：可恢复原工作目录，凭据未进入项目。

### Phase 1：私有GitHub主仓库

创建私有仓库，导入正式文件、脚本、专项Markdown和冻结基准；建立`.gitignore`、分支保护、CODEOWNERS和备份标签。验收：远端commit可追溯，工作区无未授权大文件和密钥。

### Phase 2：云端同花顺

在云Runner安装CLI/依赖，通过GitHub Secrets注入Key；将脚本改为环境变量路径和动态交易日；跑八ETF＋两A股指数快照、历史末日、失败重试和限流测试。验收：电脑关机时云Runner仍成功，日志不泄露Key。

### Phase 3：海外源

分别验收NDX、SOXQ、N225、HSTECH和黄金上游的字段、时区、收盘口径、延迟、空结果和交叉来源。验收：失败时DEGRADED，不用旧值。

### Phase 4：标准数据和CURRENT

实现节点ID、交易日闸门、supersedes、freshness、幂等、原子写和版本哈希。验收：重复运行不重复事件；新节点自动取代旧节点。

### Phase 5：节点调度

实现09:25、10:30、11:30、13:30、14:30和收盘节点；使用Asia/Shanghai和实际交易日历。验收：周末、午休、节假日、延迟、漏跑均有正确状态。

### Phase 6：通知

先接入可靠手机推送或邮件，通知只发短摘要；再尝试ChatGPT Scheduled Task/GitHub App读取CURRENT。验收：用户离线收到通知，旧节点点击后聊天读取最新CURRENT。

### Phase 7：账户与真实成交

用测试账户事实和脱敏截图验证事件ID、账户事实时间、冲突、过期和成交后立即更新CURRENT。验收：缺账户事实时不输出金额/卖出份额。

### Phase 8：四文件维护

只允许机器提交数据索引、Dashboard允许字段和经验事件；MASTER变更走人工评审。验收：规则版本、职责、无评分/标签/新权限、无非法份额。

### Phase 9：故障和回滚

模拟API失败、Git冲突、重复触发、旧通知、时区错误、日线延迟、海外闭市、账户冲突和通知失败。验收：均显示DEGRADED/BLOCKED并可恢复，不生成伪信号。

### Phase 10：正式迁移

只有Phase 0—9全部通过，才把GitHub标记为主版本并暂停本机Heartbeat。任何关键能力未通过，不宣布“云端正式上线”。

## 十六、最终上线标准

当前**不满足正式上线标准**。必须同时证明：电脑关机后云Runner仍取数；八ETF、核心指数和必要海外对象有可追溯数据；GitHub有唯一主版本且冲突不覆盖；CURRENT总是指向最新有效节点；旧通知不会误导；手机能收到通知；截图能进入正式判断；真实成交能即时留痕；四文件职责不混淆；任何关键服务异常都不会产生伪交易信号。

在这些证据完成前，系统可称为“本机自动采集与云端迁移准备阶段”，不可称为“云端正式上线”。

## 十七、最终审计判断

- 当前方案是否可执行：**有条件通过**。
- 是否必须使用ChatGPT Work：**不是必须**；云取数和状态应由GitHub Actions/等效Runner承担。Work只作可选通知和读取层。
- 是否存在职责重复：**存在**，主要是本机Heartbeat、Scheduled Task和未来GitHub Actions都可能重复取数/写状态；正式架构只保留一个数据写入者。
- 是否需要CURRENT：**需要**，它是解决旧通知、最新节点、数据新鲜度和账户事实时间的最小状态层。
- GitHub是否适合作为唯一主版本：**正式文件和状态适合；原始大数据不应全部直接进入普通Git历史**。
- 完全无人值守能做到哪一步：**行情采集、质量审计、节点快照、状态更新和短通知**；不能无人值守完成需要账户事实的金额、卖出份额和人工下单。
- 是否建议立即开始部署：**建议从Phase 0—2开始，但不建议立即宣布上线或暂停本机流程**。

当前最大风险：把本机可运行误判为云端可持续运行，并在账户事实缺失时生成看似完整的交易动作。  
判断可能错误原因：ChatGPT Work、GitHub App和用户计划的实际权限/通知能力可能与公开文档或当前界面不同，必须做账号级端到端测试。  
信息不足：尚未有目标GitHub仓库、云Runner、海外数据源、手机推送、账户事件写入链和真实交易日多节点运行证据。  
最可能失效的假设：Scheduled Task能够稳定读取私有GitHub最新CURRENT并在用户离线时按节点完成分析。  
置信度：中高。  
最可能出错的地方：调度延迟、GitHub权限/索引、海外源时点和账户截图事件写回；这些任一环节未实测都不能宣称云端上线。
