# CA01—CA11 生产变更治理收敛审计

## 结论

现行 CA01—CA11 的核心目标仍然有效，但 11 个平级条款已经出现明显语义重叠。继续逐条增加解释、例外或后续编号，会让治理层本身成为新的复杂度来源，并增加 ChatGPT/Codex/人工维护在准入判断中的认知负担。

本审计建议在不改变实质安全边界的前提下，将稳定语义收敛为四个治理原则；旧 CA 编号保留兼容映射和历史审计，不再作为日常需要逐条背诵的平级入口。

本文件只做隔离治理审计，不修改 main、生产规范、机器镜像、checker 或交易规则。

## 一、现行 11 条的职责归类

### A. 准入与时机：CA02 + CA03 + CA10

三条实际共同回答“现在是否应该立即修改生产”。

- CA02：当前正式行情/时点、账户/成交/现金或 canonical 生产链真实故障，且现有恢复不能解决时允许立即修改；
- CA03：fallback/self-healing/retry 已正确恢复的瞬态事件默认观察；
- CA10：A股连续交易期间只允许真正 FIX_NOW 的生产修改。

建议收敛为一个稳定原则：**先判断当前生产影响与现有恢复能力；只有真实当前影响且无法恢复时立即改，已恢复瞬态先观察，连续交易时只允许前者。**

### B. 根因完整修复：CA01 + CA06 + CA07 + CA08 + CA11

五条都属于同一修复哲学：不要在症状点堆补丁。

- CA01：先根因；
- CA06：最小修复必须根因完整；
- CA07：在最高合法 canonical owner 修复；
- CA08：同根因出现第二补丁时重新做完整根因分析；
- CA11：同根因多个症状视为一个修复单元。

建议收敛为一个稳定原则：**以根因为修复单元，在最高合法 owner 做最小根因完整修复；同根因多症状合并处理，若需要二次补丁则重新分析完整链路。**

### C. 范围与验证：CA04 + CA09

两条都是修复质量门。

- CA04：验证原失败、相邻边界和此前正常场景；
- CA09：保持无关合同不变，不搭车改阈值、provider、权限、频率等无关语义。

建议收敛为一个稳定原则：**修复只改已证明根因涉及的合同，并同时验证失败场景、相邻边界和原正常路径。**

### D. 独立非紧急语义串行：CA05

CA05与其他条款职责不同，应保留独立语义，但边界需要进一步收窄。

建议稳定表达为：**彼此独立的非紧急生产语义变更之间保留一个真实自然生产周期，用于验证可归因性；research-only、诊断、回测、隔离实现、测试和审查不受此限制；FIX_NOW不等待。**

OBSERVE必须有 release condition 与复核节点。动态状态刷新、research-only提交、测试产物、纯文档/审计不重置观察基准。新的独立生产语义合并后，其他待集成事项以最新成功闭环的语义变更为基准重新观察。

## 二、复杂度与执行效率审视

### 1. 现行规则的收益

- 降低瞬态故障引发过度修复；
- 避免多个独立生产语义连续上线导致故障不可归因；
- 强制 root-cause、canonical owner 和 full validation；
- 防止 main 被旧分支、平行 writer 或 force push 破坏。

这些收益具有现实价值，不建议整体撤销。

### 2. 已出现的成本

- CA01/06/07/08/11需要在同一次诊断中反复解释高度相似的根因原则；
- CA02/03/10容易被误读成“bug也要等待”或“只要已恢复就永远不修”；
- CA05容易被误读成“系统每天只能处理一个任务”；
- 为解决 CA05 遗忘又新增 Release Gate、review freshness、queue scanning 等运行逻辑，治理开始有自我膨胀风险；
- checker当前硬编码 CA01—CA11 的完整编号合同，未来若继续新增CA编号，会进一步提高文档、镜像、checker三方同步成本。

## 三、推荐的长期目标结构

建议正式治理层最终只保留四个日常可理解原则：

1. **立即修复边界**：真实当前生产影响且现有恢复不能解决才 FIX_NOW；已恢复瞬态 OBSERVE；连续交易时只允许 FIX_NOW。
2. **根因完整修复**：以根因为单位，在最高合法 canonical owner 做最小根因完整修复；二次补丁触发重新根因分析。
3. **范围与验证**：不改变无关合同；验证原失败、相邻边界和原正常路径。
4. **独立语义串行**：独立非紧急生产语义之间观察一个真实自然生产周期；研究/诊断/测试不等待；OBSERVE必须可释放、可复核、不可无限滚动。

旧 CA01—CA11 保留在迁移表中，保证历史Issue/PR/审计仍可追溯，但不继续把它们当作11个日常平级决策入口。

## 四、不应纳入长期治理规范的内容

以下属于运行事实，不应固化进规范：

- Release Gate 的具体 16:20 触发时间；
- Issue #60/#64/#65/#66 等当前编号；
- 当前待生产队列顺序；
- 某一研究对象、ETF代码或某个 commit SHA；
- 当前 workflow run id、provider事件或本周异常。

## 五、正式实施边界

正式实施时应作为同一问题域一次性修改：

- `docs/生产变更与并发写入协议_V1.0.md`：收敛稳定治理语义；
- `config/maintenance/production_mutation_protocol.json`：同步机器镜像；
- `scripts/check_production_mutation_protocol.py`：从“硬编码11个编号”转为验证少量稳定治理合同，同时保留旧编号迁移兼容；
- 必要的最小回归测试。

不得借本次收敛修改：MASTER、风险许可、Trial/Confirm、金额、卖出、provider优先级、行情时段、workflow频率、writer ownership、mutation gateway、自动交易权限。

## 六、CA05当前处理

本治理收敛本身属于非紧急生产治理语义变更，因此当前仅完成隔离审计和实施设计，不合并 main。待 CA05 允许后，必须重新读取 latest main，确认期间没有其他治理变更已覆盖本问题，再重放实施并执行 PR full consistency 预检、合并后 main full consistency + E2E。

## 最终判断

现行 CA01—CA11 **不是错误设计**；问题在于从建设期的细粒度防错条款逐渐变成了日常运行需要理解的11个平级入口。现在最合适的优化不是删除保护，而是把相同保护压缩成少量稳定原则。

目标应是：**保护不减，规则更少；研究更快，生产更稳；治理不成为新的审批系统。**
