# ETF系统复杂度与执行摩擦集中审计

## 审计定位

本审计承接 Issue #66 的 CA01—CA11 治理收敛，但范围扩大到当前 ETF 系统的检查、数据权威、研究生命周期、PR/Issue 生命周期、自动任务与防复发机制。目标不是继续增加治理，而是识别哪些复杂度必须保留、哪些可以合并、哪些只是历史演化残留、哪些需要先测量再决定。

基线：main `161c2554cb48ad956c42aa80f8e9d1b75378b69c`。

本文件为隔离审计产物，不修改 main、不改变 MASTER、provider、交易权限、风险许可、Trial/Confirm、金额、卖出、行情频率或自动交易能力。

## 一、总体结论

当前系统的主要风险已经从“缺少保护”逐渐转为“保护、状态、检查和研究流程可能继续累积”。近期仓库演化表明，大部分新增组件都有真实历史原因，但若不做成熟后的语义压缩和组件回收，局部正确会逐渐形成全局执行摩擦。

当前不建议大规模删除功能。优先级应是：

1. 先收敛权威和职责边界；
2. 再减少重复检查与脆弱测试；
3. 再压缩研究/PR/Issue生命周期管理入口；
4. 最后才评估PoC/shadow/辅助组件是否退役。

## 二、逐域审计

### 1. 生产治理准入

处置：`CONSOLIDATE`

现行 CA01—CA11 的保护目标有效，但日常入口过细。Issue #66 已形成“四条治理原则 + 少量硬工程合同”的目标结构。这里不再另建新的治理体系。

必须保留的硬合同：latest-main、禁止force push、writer ownership、formal mutation gateway、动态状态由canonical producer重建、PR/full consistency预检、main组合验收。

### 2. full consistency / local guard / self-healing / failure guard / E2E

处置：`KEEP_HARD_CONTRACT` + `CONSOLIDATE`

需要保留三种职责，但不能互相复制：

- producer local guard：在数据/状态生成当场判断局部质量；
- runtime recovery：self-healing / failure guard只负责当前运行恢复和故障路由；
- cross-system acceptance：full consistency + E2E负责跨域结构和最终组合验收。

近期 #18、#19、#26 已经沿这一方向收敛，例如可重建派生状态不再反向触发full consistency、海外runtime不再写A股runtime、完整系统检查统一由system-consistency编排。这些方向应继续保持，而不是新增第二套健康状态。

进一步动作：审计轻量production health guard是否只是只读聚合视图。如果它不产生第二判断权威、不写状态、不重复触发恢复，保留；如果后续开始产生独立结论/通知/状态，则应并回现有health/recovery入口。

### 3. 规范 / 技术说明 / 机器配置 / 状态的权威边界

处置：`CONSOLIDATE`

Issue #53 已闭环生产治理规范与机器镜像漂移；Issue #57 已识别数据规范与查询路由技术说明仍有稳定规则、动态事实、实现说明混层。

建议将“一个语义只有一种承载角色”作为稳定架构原则：

- 规范：只放稳定规则；
- 机器配置：只放当前参数/对象/owner事实；
- 状态：只放当前运行事实；
- 技术说明：只解释调用链，不重新定义规则；
- INDEX/README：只导航。

不新增新的SSOT文件。

### 4. checker / test 对文案和结构过拟合

处置：`CONSOLIDATE`

已出现两类实际摩擦：

- 科创50防漂移测试因模拟缺陷不完整造成假失败；
- 规范重构后旧测试依赖历史句子/段落位置，导致生产验收需要二次修复。

测试原则应从“文本仍存在”转为“稳定合同仍成立”。允许文本解析，但断言对象应是语义集合、owner关系、权限边界、数据资格，而不是具体句序或历史编号。

CA01—CA11 checker硬编码只是当前最明显例子。正式治理收敛时应同步修改，避免未来新增/合并规则再次造成checker结构耦合。

### 5. 研究生命周期与Issue碎片

处置：`CONSOLIDATE`

561980研究链展示了严谨性价值，也展示了管理入口膨胀：历史成分PIT → 真实调样PIT → 正式转化审查 → 生产集成。每一步的证据门都合理，但“每一步都成为独立长期管理入口”不是必需的。

建议未来采用两阶段稳定边界：

- `RESEARCH LIFECYCLE`：一个研究Issue内部允许完成数据能力、PIT修正、稳健性、对象级复核等多个research-only阶段；
- `PRODUCTION CONVERSION`：只有研究资格发生正式变化（进入MASTER 8.1审查）或真正进入生产集成时才建立新的正式入口。

不减少PIT、稳健性或8.1五维审查，只减少Issue/分支管理噪音。

### 6. latest-main 与 PR churn

处置：`CONSOLIDATE`

latest-main与串行生产集成必须保留，但近期出现 #17→#18、#34→#35、#54→#55 等“旧基线PR关闭、再开新PR”的历史噪音。

建议稳定做法：

- 研究/实现阶段尽量停留在隔离分支，不急于开正式PR；
- 只有准备进入生产预检时，才从当时latest main重建/重放一次最终生产分支并开PR；
- 如果PR已经进入正式预检后main前进，则仍按协议重放，不牺牲安全性。

这样减少“准备阶段PR”而不削弱latest-main。

### 7. PoC / shadow / capability validation 生命周期

处置：`MEASURE_FIRST`，其中部分为 `RETIRE_CANDIDATE`

当前机器镜像明确登记三条非生产验证workflow：

- `akshare-capability-poc.yml`
- `minute-source-poc.yml`
- `minute-path-shadow.yml`

分钟能力已经有相当部分正式进入生产；因此 `minute-source-poc` 和部分 `minute-path-shadow` 功能具备“使命是否已完成”的退役候选资格，但当前不能仅因存在正式分钟能力就删除。需要检查近期开启频率、是否仍提供正式producer没有覆盖的质量信息、是否承担新provider验证职责。

若连续多个生产周期没有独立信息增量，应优先关闭schedule或退役，而不是永久保留“曾经有用”的PoC。

`akshare-capability-poc`同理：如果只是历史数据源能力验证且当前没有明确未来用途，应测量后决定是否退役；如果仍承担对象级fallback能力验证，则保留artifact-only边界。

### 8. 新增能力的复杂度预算

处置：`CONSOLIDATE`

以后新增正式能力前，除功能/收益验证外，应增加一个极简问题，而不是新的审批层：

> 是否能复用现有producer、state、workflow、checker、fallback和通知入口？若不能，新增长期组件带来的收益是否明显高于维护成本？

这应作为“同问题域最小充分缺口检查”的一部分，不新增评分表或固定打分。

### 9. 自动任务与长期规范

处置：`MOVE_TO_RUNTIME_FACT` + `CONSOLIDATE`

Release Gate暴露了一个典型风险：稳定治理语义先进入自动任务prompt，随后才考虑是否固化到正式规范。

长期边界应为：

- 任务prompt：运行时间、当前Issue、扫描范围、一次运行操作步骤；
- 唯一规范：稳定准入、release condition语义、writer/权限边界；
- GitHub状态：当前队列、审查锚点、运行结果。

具体16:20、Issue编号、当前队列不得成为长期规范。

### 10. 问题闭环与永久门禁膨胀

处置：`CONSOLIDATE`

“每个事故都新增永久checker/状态/规则”会造成系统长期负担。防复发应该优先覆盖一类失效模式，而不是纪念一次事故。

新增永久门禁前至少需要确认：

1. 问题是否可能重复且实质影响生产；
2. 现有上位合同是否已经可以检测；
3. 强化现有checker是否足够；
4. 新增门禁是否会进入高频关键路径；
5. 是否存在成熟后可删除的条件。

这不是新增审批状态，只是防止一次性事故永久化。

## 三、第一批候选动作

### A. 建议保留，不动

处置：`KEEP_HARD_CONTRACT`

- latest-main；
- no force push；
- writer ownership；
- formal-file mutation gateway；
- canonical state producer；
- Point-in-Time；
- full consistency + E2E最终组合验收；
- research-only不写main；
- MASTER不由自动workflow修改。

这些是架构安全边界，不应为了“简化”删除。

### B. 已有明确方向，可进入后续收敛

处置：`CONSOLIDATE`

1. Issue #66：CA01—CA11 → 少量治理原则；
2. Issue #57：数据规范/查询技术说明/机器事实分层；
3. checker从历史文案断言转为稳定合同断言；
4. 研究Issue生命周期从多段管理入口压缩为“研究生命周期 + 正式生产转换”两层；
5. 准备阶段不急于开PR，减少latest-main重放PR churn；
6. 自动任务prompt中的稳定语义最终回归唯一规范。

### C. 需要先测量，不立即改

处置：`MEASURE_FIRST`

1. `minute-source-poc.yml`近期开启频率、独立增量、是否仍被正式能力开发使用；
2. `minute-path-shadow.yml`在分钟生产化后是否仍产生独立风险发现；
3. `akshare-capability-poc.yml`是否仍有现实provider验证用途；
4. lightweight production health guard是否只是只读聚合，还是开始与full consistency/self-healing职责重叠；
5. OBSERVE平均时长、CA05实际延迟事项数、CA03避免无效修复次数，用来判断治理收益是否值得。

这些项目在没有测量前不应删除。

## 四、建议的实施顺序

1. 先完成 Issue #66 治理语义压缩；
2. 再完成 Issue #57 权威边界收敛；
3. 同时做上述 `MEASURE_FIRST` 的只读统计，不需要等待CA05；
4. 基于统计决定是否退役PoC/shadow/辅助聚合；
5. 研究/PR生命周期优化优先通过工作方式和模板收敛，除非确实需要修改生产合同，不为它单独新建workflow/state；
6. 每次真正生产修改仍进入Release Gate，避免一次大规模“复杂度清理”反而造成组合风险。

## 五、反对的做法

- 不做“一次性大扫除”删除大量workflow/state/checker；
- 不为了管理复杂度再建一套复杂度评分系统；
- 不把Issue数量、文件数量本身当成坏指标；
- 不把所有fallback视为冗余；
- 不因为系统当前PASS就认为所有组件都有长期价值；
- 不为了追求代码整洁影响盘中行情、账户事实和正式判断时效。

## 最终判断

当前最值得优化的不是交易逻辑，而是**系统成熟后的复杂度回收机制**：新能力可以先细粒度验证，但一旦成熟，应主动收敛规则、移除重复权威、缩短管理链，并审视PoC/shadow是否仍有独立信息价值。

这次审计不建议形成新的治理子系统。后续应把复杂度回收嵌入既有“同问题域最小充分缺口检查”和Release Gate，而不是再增加第五套长期治理入口。
